# NHN Cloud 콘솔 안내 챗봇 설계

작성일: 2026-09-17
상태: 설계 승인 완료, 구현 계획 작성 전

## 1. 목적과 범위

이노그리드 컨설팅·운영팀(수십 명, 상시 사용)이 NHN Cloud 콘솔 작업 방법을 물으면, 공식 문서를 근거로 **메뉴 경로 + 단계별 절차 + 해당 화면 스크린샷**을 답하는 웹 챗봇.

- 대상 사용자: 사내 다수. 사내망 접근 제한으로 인증을 갈음한다.
- 대상 문서: docs.nhncloud.com 전체 26개 카테고리. 콘솔 사용 가이드가 핵심이며, API·개요 등 나머지 문서도 적재해 일반 질문에 답한다.
- 제공 형태: 독립 웹 페이지(Streamlit). 콘솔 내 위젯, 메신저 연동은 범위 밖.
- 기반: 현재 동작 중인 문서 RAG 챗봇(pgvector + BM25 하이브리드, LLM 리랭킹, 대화 기억, NHN Cloud 디자인 UI)을 확장한다. 전면 재작성하지 않는다.

### 1-1. 현재 상태에서 발견된 전제 문제

크롤러(`crawlling/1.menual_down.py`)가 파일을 `카테고리/문서명.html`로 저장해, 같은 카테고리의 여러 서비스가 같은 문서명("콘솔 사용 가이드", "API 가이드")으로 서로 덮어썼다. 그 결과 콘솔 사용 가이드는 26개 카테고리에 36개만 남았고(예: `Compute/콘솔 사용 가이드.html`은 Virtual Desktop 하나), 현재 431개 파일은 충돌 후 잔여분이다. **전체 재수집이 이 설계의 선행 조건이다.**

저장된 페이지의 첫 `<h2>`는 `Compute > Virtual Desktop > 콘솔 사용 가이드` 형태의 브레드크럼이므로, 이를 경로의 원천으로 쓰면 사이트 구조를 다시 분석하지 않고 해결된다.

## 2. 전체 구조

```
[수집]  crawlling/crawl.py (Selenium)
        docs.nhncloud.com → nhn_cloud_docs/{카테고리}/{서비스}/{문서명}.html
                             + 같은 폴더 images/ (원본 파일명 유지)
                             + manifest.json (문서별 원본 URL·브레드크럼·수집 시각·본문 해시)
          ↓
[적재]  app/ingest.py
        HTML → 섹션 단위 청크 (h2/h3/h4 경계)
        청크마다: 본문, 카테고리, 서비스, 문서 종류, 섹션 경로, 스크린샷 목록, 원본 URL
        → pgvector documents
          ↓
[검색]  app/rag.py
        질문 → 의도·서비스 추정(규칙) → 하이브리드 검색 → 점수 보정 → 리랭킹(근거 여부 포함)
          ↓
[답변]  app/ui.py (Streamlit)
        메뉴 경로 + 단계별 텍스트 + 단계별 스크린샷 인라인 + 원문 링크 + 👍/👎
```

| 유지 | 변경 | 신규 |
|---|---|---|
| pgvector + BM25 하이브리드, 한 번에 채점하는 리랭킹, 대화 기억, NHN Cloud 디자인 UI, Docker 구성 | 크롤러(경로 규칙·이미지 저장·URL 기록), `ingest.py`(섹션 청킹·메타데이터), `documents` 스키마, LLM 제공자 설정 | 의도·서비스 추정, 콘솔 가이드 가중치, 스크린샷 렌더링, 피드백·질문 로그, 재수집·재적재 스크립트, 평가 세트 |

구조적 결정:
- 이미지는 DB에 넣지 않는다. 파일로 두고 청크에는 경로만 저장한다. `nhn_cloud_docs/`를 app 컨테이너에 읽기 전용으로 마운트한다.
- `app/data`로 복사하는 단계를 없앤다. 적재는 `nhn_cloud_docs/`를 직접 읽는다.
- LLM 호출은 질문당 2회(리랭킹 1, 답변 1)로 고정한다. 의도·서비스 추정에 LLM을 쓰지 않는다.

## 3. 데이터 파이프라인

### 3-1. 크롤러 `crawlling/crawl.py`

기존 `1.menual_down.py`와 `2.image_down.py`를 하나로 합친다.

- 경로: 페이지 본문 첫 `<h2>` 브레드크럼을 ` > `로 나눠 `{카테고리}/{서비스}/{문서명}.html`. 2단 브레드크럼(서비스 없음)은 `{카테고리}/_/{문서명}.html`. 브레드크럼이 없으면 메뉴 링크 이름으로 대체 저장하고 manifest에 표시한다.
- 파일명 금지 문자 치환은 기존 `clean_name` 규칙을 유지한다.
- 이미지: 문서와 같은 폴더의 `images/`에 **원본 파일명으로** 저장한다(`img_0.png`로 바꾸지 않는다). HTML의 `src`를 `./images/{파일명}`으로 고친다. 다운로드 실패 시 `src`를 원본 URL로 두고 manifest에 `missing`으로 기록한다.
- `manifest.json`: 문서마다 `{path, url, breadcrumb, fetched_at, content_hash, image_count, status}`. `status`는 `ok | error | no_breadcrumb`.
- 실행 모드: 전체 수집(기본), `--changed`(본문 해시가 바뀐 페이지만). 문서 단위로 manifest에 완료를 기록해 중단 후 이어받는다.
- 예상 규모: 1,000~1,500페이지, 이미지 2,000~4,000장, 소요 1~1.5시간.

### 3-2. 적재 `app/ingest.py`

- 청킹 단위: 섹션. `h2/h3/h4` 제목부터 다음 같은 급 이상 제목 전까지.
- 섹션이 1,500자를 넘으면 문단 경계에서 나누고, 나뉜 조각마다 섹션 제목 경로(`문서명 > h2 > h3 > h4`)를 본문 앞에 붙인다.
- 첫 `<h2>`(브레드크럼)는 메타데이터로만 쓰고 섹션으로 만들지 않는다.
- 스크린샷: `<img>`를 직전 블록(p/li/td)에 소속시킨다. 청크 메타 `images = [{path, caption, alt}]`, `caption`은 직전 블록 텍스트. 본문에는 `[스크린샷 N: caption 앞 60자]` 마커를 남긴다. N은 청크 안에서 1부터. 답변 프롬프트를 만들 때 청크 5개의 이미지를 **전체 순번으로 다시 매겨**(1..M) 마커를 바꿔 넣고, 그 순번→경로 매핑을 렌더링에 넘긴다. 청크별 번호가 겹쳐 생기는 모호함을 없애기 위해서다.
- 문서 종류 `doc_type`: 문서명으로 판정. `콘솔` 포함 → `console`, `API` 포함 → `api`, `개요` → `overview`, 그 외 `other`.
- 표는 `table_to_text`(헤더: 값 쌍), 코드는 `[코드]` 블록으로 기존 방식 유지.
- 실행: 문서 단위 커밋. `source_path`와 `content_hash`가 일치하는 문서는 건너뛴다. `--rebuild`일 때만 테이블을 초기화한다. 임베딩 실패는 재시도 후 그 문서만 건너뛰고 끝에 목록을 출력한다.
- 적재 후 서비스 목록과 문서 제목에서 별칭 사전 초안(`services.generated.yaml`)을 생성한다.

### 3-3. 스키마

```sql
CREATE TABLE documents (
  id           SERIAL PRIMARY KEY,
  content      TEXT NOT NULL,
  embedding    VECTOR(2048),
  category     TEXT NOT NULL,
  service      TEXT NOT NULL,          -- 서비스 없으면 '_'
  doc_type     TEXT NOT NULL,          -- console | api | overview | other
  doc_title    TEXT NOT NULL,
  section_path TEXT NOT NULL,          -- "인스턴스 생성 > 네트워크 설정"
  source_path  TEXT NOT NULL,          -- nhn_cloud_docs 기준 상대 경로
  source_url   TEXT,
  content_hash TEXT NOT NULL,
  images       JSONB NOT NULL DEFAULT '[]'
);
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON documents (service, doc_type);

CREATE TABLE questions (
  id          SERIAL PRIMARY KEY,
  asked_at    TIMESTAMPTZ DEFAULT now(),
  question    TEXT NOT NULL,
  service     TEXT,
  intent      TEXT,                    -- console | general
  grounded    BOOLEAN,
  elapsed_ms  INTEGER,
  sources     JSONB,                   -- 상위 출처 [{source_path, section_path}]
  error       TEXT,
  feedback    SMALLINT                 -- NULL | 1 | -1
);
```

임베딩 차원은 임베딩 모델에 따르므로 `ingest.py`가 첫 호출로 자동 감지한다(현재 2048).

## 4. 검색

### 4-1. 질문 이해 (LLM 없음)

- 의도: `console` 신호어("어디서", "어떻게 해", "설정", "만들", "생성", "삭제", "메뉴", "버튼", "콘솔", "화면", "클릭")가 있으면 `console`, 없으면 `general`. 오판은 가중치만 바꾸므로 비용이 낮다.
- 서비스: 별칭 사전(`services.generated.yaml` + 수동 `services.yaml`)으로 질문에서 매칭. 여러 별칭이 걸리면 가장 긴 별칭의 서비스를 택한다("Object Storage"가 "Storage"보다 우선). 매칭 결과는 필터가 아니라 부스트에 쓴다. 사이드바에서 서비스를 고정하면 추정 대신 그 값을 쓴다.
- 대화 맥락: 후속 질문이면 직전 질문을 검색 질의에 붙이고(현재 구현), 직전 턴의 서비스를 이어받는다.

### 4-2. 후보 검색과 점수 보정

- 벡터: 코사인 상위 20. BM25: 상위 20.
- BM25 토크나이저: 한글은 2-gram, 영문·숫자는 단어 그대로. 형태소 분석기 의존성을 추가하지 않는다.
- 합치기: 순서 유지 중복 제거 후 곱셈 보정.
  - `doc_type == console`이고 의도가 `console`: ×1.5
  - 서비스 매칭: ×1.3
  - 벡터·BM25 모두에 등장: ×1.2
- 상위 12개를 리랭킹에 넘긴다.

### 4-3. 리랭킹

한 번의 호출로 12개를 채점한다(현재 방식). 문서당 900자로 잘라 넣는다. 점수(0~10)와 함께 "이 문서에 답이 있는가(예/아니오)"를 받는다. 최종 5개 중 "예"가 없으면 `grounded = false`. 파싱 실패 시 검색 순서를 쓰고 `grounded = null`(관련도 확인 실패).

### 4-4. 답변 단계로 전달

청크 5개(본문·섹션 경로·images·source_url), 추정 서비스, 의도, `grounded`.

## 5. 답변과 UI

### 5-1. 답변 생성

- `grounded == false`: LLM에 검색 결과를 넘기지 않고 고정 문구("제공된 문서에서 확인되지 않습니다. 관련 서비스: X")만 표시한다. 출처를 표시하지 않는다.
- `grounded == null`: 답변은 생성하되 출처 위에 "관련도 확인 실패"를 표시한다.
- `console` 의도 형식: 첫 줄 메뉴 경로(`콘솔 > Network > VPC > Subnet`) → 번호 목록 단계, 스크린샷이 있는 단계 끝에 `{{img:N}}` 마커 → 문서에 "주의/참고"가 있을 때만 주의사항.
- `general` 의도 형식: 현재 프롬프트 유지(절차는 번호 목록, 파라미터는 표).
- 시스템 프롬프트의 근거 제한 문구와 대화 맥락 해석 지시는 유지한다.

### 5-2. 스크린샷 렌더링

1. 스트리밍 중에는 텍스트를 그대로 표시한다(마커 문자열 노출 허용).
2. 완료 직후 같은 자리를 다시 그려 `{{img:N}}`을 `st.image(path)` + 캡션(caption 앞 60자)으로 치환한다. N은 프롬프트 생성 때 매긴 전체 순번이며, 순번→경로 매핑은 답변과 함께 세션에 저장해 대화 기록을 다시 그릴 때도 쓴다.
3. 마커 번호가 매핑 범위 밖이면 마커를 제거하고 로그에 남긴다.
4. 이미지 파일은 마운트된 `nhn_cloud_docs/`에서 직접 읽는다. 별도 정적 서버는 두지 않는다.

### 5-3. UI 변경

| 위치 | 변경 |
|---|---|
| 답변 상단 | 추정 서비스 태그 |
| 참고한 문서 | 문서명 칩을 원문 URL 링크로. 본문 미리보기 대신 섹션 경로 |
| 사이드바 | "검색 후보 수" 슬라이더 제거. 서비스 선택 드롭다운 추가(선택 시 해당 서비스 부스트 고정) |
| 예시 질문 | 콘솔 절차형 4개로 교체 |
| 답변 하단 | 👍/👎 버튼. `questions.feedback`에 저장 |

## 6. LLM 제공자와 운영

### 6-1. LLM 제공자

`llm.py`가 OpenAI 호환 API를 쓰므로 `.env`의 `BASE_URL`·키·모델명만 바꾸면 제공자를 교체할 수 있다. 현재 NVIDIA NIM 무료 티어는 질문 하나에 429가 반복돼 상시 사용에 부적합하다. 선택지:

1. NVIDIA NIM 유료 — 코드·모델 그대로. 한도·과금 확인 필요.
2. 다른 OpenAI 호환 API — 프롬프트 재검증(반나절) 필요.
3. 사내 GPU에 vLLM 자체 호스팅 — 외부 유출 없음. GPU·운영 부담. 임베딩 모델도 함께.

첫 버전은 1 또는 2로 시작하고 3은 별도 결정으로 둔다. **임베딩 모델을 바꾸면 재적재이므로 제공자는 전체 재수집 전에 확정한다.**

### 6-2. 배포

- `docker compose up -d`로 db + app이 서비스 상태가 된다. app용 Dockerfile을 만들어 의존성을 이미지에 넣고 `streamlit run ui.py`를 기본 명령으로 한다.
- `nhn_cloud_docs/`는 app에 읽기 전용 볼륨. DB는 named volume.
- 사내망 리눅스 서버 1대에 배포, `http://<서버>:8501`. 별도 로그인은 두지 않는다.
- BM25 인덱스는 프로세스 메모리에 있으므로 재적재 후 app 재시작이 필요하다. 재적재 스크립트가 마지막에 수행한다.

### 6-3. 로그·피드백·재수집

- 질문마다 `questions`에 기록한다. 사용자 식별 정보는 저장하지 않는다.
- 주 1회 확인: 👎 비율 높은 서비스, `grounded = false`로 끝난 질문(문서 부족 또는 별칭 누락), 응답 30초 초과.
- 월 1회 `refresh.sh`: `crawl.py --changed` → `ingest.py`(바뀐 문서만) → app 재시작. 처음엔 수동 실행, 안정성 확인 후 cron.

## 7. 오류 처리

| 단계 | 실패 | 처리 |
|---|---|---|
| 크롤러 | 페이지 로딩 실패·브레드크럼 없음 | 건너뛰고 manifest에 기록. 브레드크럼 없으면 메뉴 이름으로 대체 저장 |
| 크롤러 | 이미지 다운로드 실패 | `src`는 원본 URL 유지, `missing` 기록. 답변에서 해당 스크린샷만 생략 |
| 적재 | 임베딩 API 오류 | 재시도(5회 백오프) 후 그 문서만 건너뜀. 재실행 시 미적재 문서만 처리 |
| 검색 | DB 연결 실패 | 안내 배너 + 입력 비활성화 (현재 구현) |
| 검색 | 리랭킹 실패 | 검색 순서 사용, `grounded = null`, "관련도 확인 실패" 표시 |
| 답변 | 스트리밍 시작 전 오류 | 재요청 (현재 구현) |
| 답변 | 스트리밍 도중 중단 | 받은 부분까지 표시하고 "답변이 중단되었습니다" 표시 |
| 답변 | 잘못된 스크린샷 마커 | 마커 제거, 로그 기록 |
| 답변 | `grounded = false` | 고정 문구 + 추정 서비스만 표시 |
| 운영 | 재적재 중 질의 | 문서 단위 커밋이라 서비스 지속. app 재시작(약 30초)은 업무 시간 외 |

원칙: 부분 실패는 전체를 멈추지 않는다. 실패는 반드시 manifest 또는 `questions`에 남긴다.

## 8. 테스트와 완료 기준

### 8-1. 자동 테스트 (`app/tests/`, pytest)

- 크롤러: 브레드크럼 → 경로 변환, 파일명 치환, 2단 브레드크럼, 브레드크럼 없음
- 청킹: 섹션 분할 수, 이미지의 직전 블록 소속, 1,500자 초과 분할 시 섹션 경로 부착, 표·코드 보존
- 질문 이해: 의도 판정 20문장(콘솔 10, 일반 10), 서비스 별칭 매칭 15건
- BM25 토크나이저: "인스턴스를 생성" ↔ "인스턴스 생성" 동일 문서 검색
- 점수 보정: 세 가지 보정이 순서를 바꾸는 방향
- 마커 치환: `{{img:N}}` 분할, 범위 밖 번호 제거
- LLM·DB가 필요한 테스트는 `-m integration`으로 분리

### 8-2. 품질 기준 (배포 전 통과 조건)

평가 질문 30개(`eval/questions.yaml`): 콘솔 절차 20(카테고리 고루), 일반 5, 문서 밖 5. 각 질문에 정답 문서 경로를 적는다. `python eval.py`로 재실행한다.

| 항목 | 기준 |
|---|---|
| 검색 적중 | 상위 5개에 정답 문서 포함 ≥ 80% (24/30) |
| 콘솔 답변 | 메뉴 경로 일치 ≥ 90%, 스크린샷 1장 이상 표시 ≥ 80% (콘솔 20문항 기준) |
| 문서 밖 질문 | 5개 모두 "확인되지 않음" + 출처 미표시 |
| 응답 시간 | 중앙값 15초 이하, 최대 30초 (제공자 확정 후 측정) |
| 오류 | 30문항 중 화면 오류 0건 |

## 9. 구현 순서

1. 크롤러 수정 → 카테고리 2개 시범 수집으로 경로·이미지·manifest 확인
2. 청킹·스키마·적재 수정 → 시범 수집분으로 적재, 단위 테스트 통과
3. 검색: 질문 이해, 토크나이저, 점수 보정, 리랭킹 근거 판정
4. 답변·UI: 프롬프트, 마커 치환·스크린샷, 서비스 태그·링크·피드백, `questions` 로그
5. LLM 제공자 확정 → 전체 재수집 → 전체 재적재
6. 평가 30문항 작성·실행 → 미달 항목 튜닝 → Dockerfile·compose 정리 → 배포

3~4는 시범 데이터로 개발하므로 5의 재수집과 병렬 진행 가능.

## 10. 범위 밖 (이번 버전에서 하지 않는 것)

- 콘솔 내 위젯, 메신저 연동
- 로그인·사용자별 이력
- 절차의 LLM 전처리(구조화 JSON) — 필요해지면 이 설계 위에 얹는다
- 사내 GPU 자체 호스팅 — 별도 결정
- 형태소 분석기 도입
- cron 자동 재수집 — 수동 운영으로 안정성 확인 후
